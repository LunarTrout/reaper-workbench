# R3 — контракт проектирования перед реализацией

## Зачем нужен этот этап

R2 завершил исследование шести областей и межтематическую сверку. Цель R3 — превратить эти результаты в один согласованный план сборки текущей библиотеки REAPER Workbench. По окончании R3 должно быть понятно, какие существующие модули переиспользовать, какие контракты между ними закрепить, какие изменения делать по шагам, чем подтвердить каждый шаг и что пока заблокировано живой проверкой.

R3 — этап проектирования. Он не должен менять Python/Lua код, MCP-схемы, зависимости, конфигурацию, проект REAPER или пользовательские медиа. Агенты читают код и тесты, описывают конкретный план и тестовые случаи, но тесты не запускают и не добавляют. Код начинается после интегрированного плана R3.

## Целевой результат библиотеки

REAPER Workbench должна стать чистой production-ready библиотекой для широкого музыкального ремесла в REAPER: понимать устройство проекта и связанный с ним звук, анализировать и сравнивать микс и источники, безопасно редактировать аудио, MIDI, FX, автоматику, маршрутизацию и другие проектные объекты. Модель не получает жанровый рецепт или фиксированный pipeline. Она получает хорошо связанный контекст, обнаруживаемые возможности и проверяемые операции, из которых может собрать путь к пользовательской цели.

Интеграция с REAPER остаётся нативной — документированный ReaScript API, Lua внутри REAPER, Actions и штатный render/audio access. Запрещены Frida, чтение/изменение приватной памяти процесса и любые недокументированные обходы. Полнота возможностей не означает показ LLM сотен одинаково представленных функций одновременно.

Ключевое требование — достаточный и правдивый слуховой контекст. Вывод о звуке должен ссылаться на фактически доступный аудиоматериал, временной диапазон, источник и стадию сигнала; URI или имя файла не доказывают, что модель реально получила звук. Сырые измерения, результат listener-модели, музыкальная гипотеза и проверенное состояние проекта — разные типы свидетельств.

Ограничения владельца: одна NVIDIA Tesla V100 16 GB; inference на CPU запрещён. Не предполагать наличие DI: для текущего vers1 R2 указывает amp-print для гитар. Темп/размер могут меняться автоматизацией. Промежуточные проекты и стемы нельзя копить: сохранять только исходную точку и финал; временные capture-файлы должны иметь явное владение, срок жизни и удаление. Сохранение проекта не должно затирать существующий файл или порождать неограниченные версии.

## Исходные документы и правила доказательности

Каждый агент обязан прочитать этот контракт, все шесть R2-финалов из work/research/round-2/reports и все шесть R3-брифов. Кроме них прочитать релевантные README/ARCHITECTURE/SAFETY/VALIDATION, текущие реализации и существующие тесты. Для фактических утверждений о текущем поведении приоритет имеют исходный код и воспроизводимые тесты; для семантики REAPER — официальный ReaScript reference и подтверждённые версии. R2 задаёт требования и исследовательские выводы, но не заменяет проверку фактического кода.

Для каждого утверждения указывать, что это: подтверждённый факт в коде/тесте/источнике, вывод из нескольких фактов, предлагаемое решение или неизвестное, требующее эксперимента. Любая предлагаемая схема или порог — proposal до принятия владельцем. Не превращать измерение в диагноз причины без причинного свидетельства.

Текущий checkout при подготовке R3 имел HEAD 86b14bb5136c9a0b00be4d6948986511be2d9674 и незакоммиченные изменения как минимум в docs/AI-MIX-SURFACE.md, docs/TZ.md, scripts/reaper_bridge.lua, а также untracked docs/EDITING-ACCEPTANCE.md и docs/research/. Каждый агент обязан заново проверить git status и HEAD в начале работы. Это общий рабочий checkout: запрещено сбрасывать, перезаписывать или «чистить» чужие изменения. В итогах отличать изменения текущего дерева от commit HEAD.

В дереве уже есть analysis (audio, bundle, artifacts, events, temporal, tempo, timeline_context, metrics, mix_evidence, compare, phase, partial, flamingo, ossicle и др.), daw (session, editing, alignment, delivery, cycle, EQ/limiter), reaper bridge/API catalog, MCP server и значительный набор tests. Это только стартовая карта: проследить реальные вызовы и владельцев данных, не судить по имени файла.

Есть видимое расхождение документации: docs/ARCHITECTURE.md заявляет 12 MCP tools и 5 resource templates, тогда как docs/MCP-README-LLM.md заявляет 19 tools и 5 templates. R2-05 рассматривает 14 tools/10 resources как гипотезу, подлежащую оценке. Никто не должен копировать одно из этих чисел как факт: получить список из актуального кода/схем, обнаружить рассинхрон README и архитектурного документа, предложить один проверяемый источник истины и способ выбора интерфейса по task evaluation.

## Общий контракт данных — предмет согласования R3

R2 требует единую зависимую модель. Агенты должны предложить согласованную реализацию существующими библиотечными средствами, проверить нижеприведённые кандидаты и закрепить точные названия/версии в интеграционном blueprint. Не строить graph database автоматически: R2-05 рекомендует graph-семантику на relational store + append-only evidence/action ledger, scoped dependency sets и компактный manifest с запрашиваемыми views.

1. **Идентичность и ревизия проекта.** Project ID, epoch/counter/fingerprint или аргументированная эквивалентная схема; ссылки на дорожку/item/take/FX/маркер используют стабильные GUID, а индексы считаются локальными hints. Любой read/write-контекст связан с ревизией.
2. **Время.** Типизированное time_basis и явные преобразования как минимум между source/file sample time, project time, performed time и notational time. Tempo/time-signature automation — часть карты, не одно скалярное BPM. У каждого окна и события есть границы, точность и применённое преобразование; latency/PDC offset не теряется.
3. **Звук как свидетельство.** Asset/evidence ID, источник/объект, capture_method отдельно от source_kind, строгая stage, channel view/layout, окно, sample rate, render/capture settings, project revision, latency offset, hash, ownership/lease, delivery status. Master, track, bus и другие точки сигнального тракта не смешивать под общим словом stem.
4. **Наблюдение, интерпретация и намерение.** Измерение и выход модели — Observations; нота/атака/бит/рифф/сегмент/причина — Candidate/Hypothesis с доказательствами, альтернативами, уверенностью и методом. Пользовательская цель и намеренные особенности — отдельные annotations. MIDI, присутствующий в проекте, доказывает состояние проекта, но сам по себе не доказывает слышимую ноту.
5. **Связи.** Узлы и typed edges выражают part-of, source-of, routed-to, evidence-for, occurs-at, repeated-as, intended-as, caused-by (только как гипотеза), changed-by, confirms/refutes. Зависимости анализа перечисляются явно; при изменении состояние инвалидирует только затронутые выводы, без ложной глобальной актуальности.
6. **Действие и доказательство результата.** OperationPlan адресует GUID-объекты и revision, имеет предусловия, scope, expected-after, state delta, побочные эффекты, отмену/восстановление и критерии readback. Verification ссылается на фактическое состояние и повторно снятые звуковые свидетельства; pass/fail/inconclusive не подменяются текстовым успехом.
7. **Контекст для LLM.** Начальный обзор должен быстро сообщить модель проекта, важные изменения, покрытие доступного звука/данных, stale/unknown/contested claims и доступные действия. По запросу можно перейти от глобального обзора к секции, маршруту, дорожке, FX, событию или синхронному аудиофрагменту. Большой проект не передаётся как неразличимый blob; при этом никакая функция не становится необнаружимой из-за малого фиксированного набора tools.

Это межтемный контракт, а не требование поместить всё в одну Python dataclass или в один MCP response. Агенты должны предложить, какие сущности должны быть persistently stored, какие вычисляются по запросу, какие ресурсы ephemeral и как сохраняется происхождение.

## Зависимости между шестью направлениями

- R3-05 владеет общей семантикой ID/revision/time/evidence/claim/dependency и способом выдачи контекста. Он согласуется с владельцами остальных доменов, но не изобретает их анализаторы.
- R3-01 производит звуковые assets, окна, signal measurements и listener results; это вход R3-02 и R3-04.
- R3-02 превращает сигнал в осторожные события/ноты/исполнительские жесты; события и варианты — вход R3-03 и основание допустимых монтажных действий R3-06.
- R3-03 строит метрические и структурные гипотезы с альтернативами и evidence clips; edit intent/target/protected events передаются R3-06.
- R3-04 связывает акустическое свидетельство с обоснованными миксовыми claims, референсами и экспериментами; proposed target/verification criteria передаются R3-06.
- R3-06 исполняет проверяемые операции, возвращает state delta и новую evidence lineage в R3-05 и заново снимает входы соответствующих аналитических доменов.

Каждый агент должен назвать upstream/downstream интерфейсы, стабильные контракты, что может развиваться независимо и что блокирует соседей. Любое изменение общей сущности требует предложения одного канонического типа, а не локального дубликата.

## Требования к каждому R3-отчёту

Сохранить отчёт только в свой файл work/research/round-3/reports/R3-0N-....md. Не создавать partN/v2/final-копии; при недоступности перезаписи обновлять собственный файл атомарно либо явно попросить родителя объединить патч. В отчёте обязательны:

1. Краткое решение и область, за которую агент отвечает.
2. Таблица R2-вывод → текущая реализация (file::symbol и конкретный тест/документ) → статус: confirmed / partial / missing / unknown → предлагаемое изменение.
3. Архитектурная граница: новые/изменяемые интерфейсы, владелец, поля/типы/ошибки/инварианты и совместимость. Предложение помечать proposal до принятия.
4. Пошаговый coding backlog с ID задач, точными файлами/символами, prerequisite IDs, независимыми workstreams, порядком, deliverable и exit gate. При неизвестной точке входа исследовать код вместо выдумывания file path.
5. План тестов (не запускать и не добавлять сейчас): unit/property tests; fixture/contract tests; REAPER live/copy tests; audio/LLM/human evaluation, если применимо. Для каждого — input, ожидаемое утверждение, измеримый pass/fail/inconclusive критерий и риск ложного pass.
6. Матрица риска/отката и случаев отказа: stale revision, ambiguity, unsupported stage, missing audio delivery, routing leak, non-invertible render, plugin/PDC/tail, file collision, provider/GPU limit.
7. Неизвестные вопросы: какой тест их решает, кто/что нужно, блокируют ли они код, можно ли сделать интерфейс до ответа.
8. Зависимости от пяти других R3-агентов и обязательная обратная связь им; конфликты и выбранная рекомендация с обоснованием.
9. Основания: файлы/символы/тесты и точные URL/версии, если использована документация извне. Не повторять библиографические списки из R2 без связи с кодом.

**Готовность к реализации** по задаче наступает только если понятны вход/выход, инварианты и error semantics, владелец, существующие call sites, тестовый oracle, предусловия/откат и зависимости. Если этого нет, записать блокирующее решение/эксперимент, не маскировать неопределённость псевдокодом.

## Требования к интегратору Hermes

Запустить ровно шесть субагентов по шести R3-брифам; родитель интегрирует и не создаёт седьмого исследователя. Сначала всем раздать общую цель и обязательное чтение всех шести R2-финалов и R3-брифов. После черновых R3-отчётов каждый агент должен прочитать другие пять, обновить свой раздел зависимостей и дать обратную связь по противоречиям. Родитель принимает отчёты, разрешает только документальные конфликты, не выдаёт допущения за факты и формирует:

- docs/research/round-3/IMPLEMENTATION-BLUEPRINT.md — общую архитектуру, canonical contracts, порядок сборки, интерфейсы модулей и последовательность задачи → проверка;
- docs/research/round-3/DECISION-LEDGER.md — решения, proposals, owner decisions, empirical blockers, источники и статус каждого;
- work/research/round-3/reports/R3-01…R3-06 — шесть финальных дизайн-отчётов.

Blueprint должен иметь карту зависимостей и одну таблицу фаз P0…Pn: prerequisite, scope, точные области кода, ожидаемые артефакты, тестовые уровни, exit gates, rollback и блокирующие неизвестные. В конце дать чёткий список того, что можно кодировать первым независимо, что нельзя начинать до измерений, и какой минимальный срез соединит звук → контекст → вывод → безопасное действие → звуковая проверка. Это план для последующего начала сборки, не кодовый PR.

## Контрольные запреты и ограничения

- Не менять production code, tests, project/media, configuration, dependency lockfiles, README или пользовательские файлы.
- Не запускать тесты, live REAPER, render, модельный inference или долгий benchmark в этом раунде; только проектировать, читать и при необходимости делать read-only code inspection.
- Не загружать пользовательский аудиоматериал в интернет и не запускать inference на CPU. Для будущего V100 теста описать точные предусловия/VRAM/метрики; сейчас его только планировать.
- Не утверждать, что audio URI означает, что модель слышала звук; не считать AudioAccessor полноценным stem или master до проверки.
- Не задавать hard-coded жанровые цепочки микса/монтажа/MIDI. Acceptance scenarios проверяют универсальность возможностей, но не превращаются в product workflows.
- Не добавлять каталог API целиком в LLM prompt. Не терять полный discovery к API и generic ReaScript/Actions.
- Не копить render/stem версии. Никакое сохранение не имеет права молча перезаписать существующий файл.
- Не трогать чужие изменения в общей рабочей копии и не считать текущий dirty tree своим.
