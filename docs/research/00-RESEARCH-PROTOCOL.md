# Исследовательский пакет: REAPER Workbench

**Дата среза:** 2026-11-12, Europe/Moscow  
**Этап:** исследование и решения; реализацию не начинать.  
**Исполнители:** ровно шесть исследовательских сабагентов Гермеса и один синтезатор результатов.

## 1. Цель проекта

Нужно сделать одну библиотеку, через которую языковая модель сможет работать в REAPER со всем музыкальным проектом после того, как человек записал физические инструменты. В область входят понимание звучания и структуры, ноты и MIDI, редактирование, аранжировка, обработка, сведение, мастеринг, сравнение с референсами, проверка и экспорт.

Система должна давать модели достаточно насыщенный слуховой и проектный контекст для самостоятельных решений, а затем позволять ей проверить, что сделанное действительно улучшило звук. Жанровые рецепты и обязательные фиксированные пайплайны не задаются. Модель выбирает доступные средства под цель пользователя; library supplies evidence, project state, native operations and verification.

Главный риск, который требуется исследовать: модель может получить неполную или неверно связанную картину аудио и проекта, сделать уверенный вывод, а затем начать смещённо действовать. Слуховой контекст — приоритет №1; связный контекст проекта и анализов — приоритет №2.

## 2. Обязательное ограничение оборудования

- Единственный доступный GPU для локального вывода моделей: **одна NVIDIA Tesla V100, 16 ГБ VRAM**.
- CPU-инференс запрещён. Не предлагать CPU fallback, CPU offload либо решение, требующее дополнительной GPU.
- Все шесть сабагентов работают параллельно в режиме исследования. Не запускать параллельные GPU-задачи. Если эксперимент на V100 необходим для окончательного решения, описать тест и спросить Hermes до его запуска; выполнение должно быть последовательным.
- Для каждой модели фиксировать реальную память, тип квантования, допустимую длину входа, поддержку стерео, скорость, лицензии и известные ограничения. Не считать заявленную возможность доказанной без проверки.

## 4. Правила исследования

1. Начать с вопроса решения и конечного поведения ИИ, затем установить текущую реализацию, затем искать внешние решения. Не выдавать повторное описание существующего кода за найденный пробел.
2. Использовать широкий поиск на английском и других релевантных языках. Допустимы научные статьи, официальная документация, исходный код, модельные карточки, бенчмарки, issue-трекеры, дискуссии разработчиков, форумы звукоинженеров, практические разборы и личные наблюдения. Для каждого источника оценить доказательность, дату, применимость к тяжёлой/искажённой музыке и V100.
3. Проверять цепочки ссылок: использованные проектами модели, зависимости, бенчмарки, Issues/PR и цитируемые методы. Искать альтернативные названия задач и отрицательные результаты.
4. Не заявлять «SOTA» по одному популярному репозиторию или статье. Сравнить лучшие известные подходы по качеству, входным данным, лицензии, железу, длине материала, задержке и способности выдавать проверяемый результат.
5. Продолжать поиск, пока не найден лучший evidence-supported вариант, реально совместимый с целью и одним V100 16 ГБ, и пока два последовательных раунда поиска не перестанут давать новые практически значимые методы или ограничения. Это операционное условие насыщения, а не заявление, что весь мировой поиск математически завершён.
6. Если решения, надёжно закрывающего проблему, не существует, явно сказать это; представить лучший осуществимый вариант, его пределы и остаточную неопределённость. Не объявлять тему решённой ради окончания.
7. Каждое утверждение связывать с источником. Указывать дату доступа, версию/commit/revision, где применимо. Отделять подтверждённый факт, вывод, гипотезу и личное мнение.
8. Не изменять исходный код, README продукта, настройки, RPP, model files, окружение или пользовательские данные. Разрешены только шесть research reports в work/research/reports/ и согласованный срез/индекс исследования, если Hermes его попросит. Не запускать REAPER и не изменять проект.
9. Не скачивать гигабайтные веса и не занимать V100 во время параллельного исследования. Ссылки, размеры, лицензии и план теста собрать без исполнения.

## 5. Одинаковые поля отчёта для каждого сабагента

Каждый отчёт должен содержать:

1. Краткий ответ на назначенный вопрос и почему он важен для пользовательской цели.
2. Инвентаризацию нашего проекта: файлы/функции/тесты; отдельно «есть в коде», «доступно через MCP», «проверено офлайн», «проверено в REAPER», «проверено сквозным сценарием».
3. Точное описание требуемого поведения ИИ и минимально достаточного слухового/проектного входа.
4. Широкую таблицу внешних решений: подход/модель/репозиторий, тип доказательства, качество на тяжёлой музыке, стерео, V100 16 ГБ, лицензия, скорость/память, зрелость, интеграционные затраты.
5. Ошибки и слепые зоны методов; как обнаруживать ошибки, калибровать уверенность и представлять альтернативы.
6. Предлагаемую интеграцию в существующий проект: входные данные, выходная схема, MCP-путь, привязка к revision/track/time/audio resource. Не писать реализацию.
7. Предлагаемый воспроизводимый тест на нашей задаче: корпус/ground truth, метрики, экспертная оценка и критерий принятия. Не придумывать порог без обоснования; если порог требует владельца, отметить это.
8. Рекомендацию: лучший вариант, резервный вариант, что переиспользовать, что отложить/удалить после решения, стоимость компромиссов и открытые зависимости.
9. Источники с прямыми ссылками, точными версиями, датой и указанием, какое утверждение они подтверждают. Включить поисковые запросы/ключевые термины, которыми найден результат.
10. Межтематические зависимости: какие решения других сабагентов необходимы и где их вывод может конфликтовать с вашим.

Не возвращать только общие идеи, перечень библиотек или сводку поисковых результатов. Цель — концентрат, позволяющий принять конкретное архитектурное решение.

## 6. Координация шести сабагентов

Запустить ровно шесть сабагентов — по одному на файлы 01–06. Всем передать этот протокол и полный пользовательский контекст. Каждый выполняет глубокое исследование своей темы и короткую проверку всей цепочки: звук → интерпретация → проектный контекст → MCP → действие → проверка. Синтезатор устраняет дублирование и противоречия, но не скрывает их.

Итоговая сводка после сабагентов должна дать матрицу: требование / текущее состояние / доказательство / пробел / варианты / решение / критерий проверки. Только после этого готовить план действий и делить реализацию.
