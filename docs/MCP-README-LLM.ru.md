# REAPER Workbench MCP — руководство для языковой модели

> **Статус: первая реализация.** Сервер запускается как
> `python -m reaper_audio.mcp_server` (stdio). Сейчас в `tools/list` 12 tools и
> 5 URI templates. Проверены регистрация/schema, покрытие всех 732 записей
> каталога и структурированный поиск. Живой stdio-to-REAPER запуск, чтение
> проекта и анализ пяти секунд (11 дорожек + master) с последующим release
> проверены в REAPER 7.84 на тестовой копии. Сквозной MCP edit
> preview/apply/readback/undo и передача audio resources модели ещё требуют
> проверки. Сервер не готов к выпуску. Точные схемы — в фактическом `tools/list`.

## Для чего нужен этот интерфейс

Этот сервер даёт модели широкий, проверяемый доступ к REAPER: понять
состояние проекта, прочитать или изменить дорожки, items, FX, маршрутизацию,
автоматизацию, MIDI, темп, транспорт и другие доступные возможности ReaScript.
Он также должен позволять получить для анализа звук всех дорожек, шин и мастера
с измерениями и контекстом проекта.

Пользователь задаёт музыкальную цель своими словами. Сервер предоставляет
обнаруживаемые операции и достоверное состояние REAPER. Он не задаёт жанровые
рецепты, последовательность сведения или специальную функцию для каждого
сценария. Если цель можно выполнить доступными общими операциями, собери их в
короткий, связный и проверяемый план. Не придумывай отсутствующие возможности.

Главное правило: **сначала установи, что реально доступно и что сейчас в
проекте, затем действуй по цели пользователя и проверь фактический результат**.

## Текущая карта tools

| Tool | Назначение |
|---|---|
| `reaper_session` | Проверить соединение, выбрать экземпляр REAPER, перечислить открытые проекты. |
| `reaper_capabilities` | Получить краткий индекс доменов или постранично открыть функции конкретного домена. |
| `reaper_api_search` | Найти API или Actions по карточке `object` + `operation` + `qualifiers`. |
| `reaper_project` | Снять контекст одной ревизии: master, tracks, routing, tempo, затем по запросу items/FX/MIDI. |
| `reaper_analyze` | Одним вызовом захватить и проанализировать все дорожки и мастер; вернуть источники, значения и URI отчёта/аудио. |
| `reaper_mix_evidence` | Сгруппировать измерительные свидетельства готового анализа; не выбирает обработку и не меняет проект. |
| `reaper_edit_map` | Получить кандидаты резов и свидетельства по стыкам из существующего анализа, без правки проекта. |
| `reaper_edit` | Превью, применить или отменить пакет поддерживаемых транзакционных правок. |
| `reaper_api_call` | Вызвать любую функцию из официального каталога REAPER с типизированными аргументами. |
| `reaper_action` | Искать Action или вызвать его в главной секции либо MIDI Editor. |
| `reaper_save` | Явно сохранить текущий проект или выполнить Save As с защитой от перезаписи. |
| `reaper_release` | Немедленно удалить manifest-owned WAV и отчёт конкретного анализа. |

### Анализ и сравнение с референсом

`reaper_analyze(start_s, end_s)` задаёт диапазон **проекта**. `reference_paths`
анализирует каждый файл целиком. Для конкретного фрагмента референса укажи
`reference_windows` с собственными `path`, `start_s`, `end_s` и необязательным
`name`; эти секунды отсчитываются от начала соответствующего файла, независимо
от диапазона проекта. Не предполагай, что участок проекта 40–48 с совпадает с
участком референсной песни 40–48 с. В ответе `reference_inputs` показывает,
какие окна фактически сравнивались.

`reaper_mix_evidence(analysis_id=...)` собирает измерительные свидетельства
существующего анализа и вопросы для дальнейшего решения. Пороги этого
сводного представления — эвристики для отбора; это не целевые значения и не
рецепт сведения. Отсутствие флага не доказывает отсутствие проблемы.

Для каждого источника смотри `capture.signal_stage`:
`reaper_rendered_track_stem` — рендер отдельной дорожки;
`reaper_rendered_master_mix` — полный выход мастера. `capture.time_window` и
`capture.capture_revision` указывают точный отрезок и исходное состояние проекта
для аудио. `project.revision` — текущая ревизия REAPER после захвата; используй
её для следующей правки. Штатный render временно задаёт параметры рендера и
выделяет дорожки, затем восстанавливает их; монотонный счётчик изменений REAPER
может вырасти, хотя библиотека проверила восстановление контекста и настроек.
Между
последовательными вызовами сопоставляй предыдущую `project.revision` со следующей
`project.capture_revision` и перечитывай контекст, если была возможность правки.
После изменений разные ревизии для отчётов «до» и «после» ожидаемы. Корреляция
одного стема с полным мастером не проверяет корректность: это разные сигналы, а
маршруты, шины и обработка мастера влияют на их связь. Каждый stem и мастер
анализируй отдельно; проверка реконструкции микса должна учитывать весь маршрут
сигнала.

Отдельного tool на каждую из 732 функций нет. Не делай вывод, что операции нет,
пока не проверил карту, структурированный поиск, официальный каталог и общий
`reaper_api_call`. Transaction preview поддерживает только перечисленные в
`reaper_capabilities` операции; для остальных ищи API или Action и учитывай,
что универсальный вызов не гарантирует undo.

## Масштаб задач

Пользователь может поручить любой открытый этап музыкальной работы в REAPER:
организацию и запись материала, MIDI, аранжировку и монтаж, FX и маршруты,
автоматизацию, панорамирование, сведение, анализ и экспорт. Используй
обнаруженные операции API, Actions и другие штатные возможности; если
возможность отсутствует или не проверена, сообщи это явно.

Сохраняй связь каждого решения с текущим проектом, объектами и временным
контекстом. При записи изменений работай с конкретной ревизией и стабильными
идентификаторами, затем читай состояние обратно и проверяй результат. Не
продолжай с устаревшими данными после изменения проекта.

Применяй знания звукорежиссуры как контекстные ориентиры, а не как обязательные
цифры или универсальные рецепты. Панорамирование, обработка и другие решения
зависят от исходного материала, аранжировки, референсов и пожелания пользователя.
Не зашивай их в MCP как готовый порядок действий.

## Как выбирать инструменты

В каждом запуске сначала ориентируйся на фактический список `tools/list` и
описания ресурсов сервера. Он является источником точных имён, аргументов и
ограничений. Этот README объясняет модель работы, но не заменяет схемы
вызовов.

Интерфейс не стремится к наименьшему числу инструментов. Он должен покрывать
возможности REAPER так, чтобы модель находила нужную операцию без необходимости
загружать в контекст сотни сигнатур. Используй уровни доступа:

1. **Инструмент понятного домена** — для частой типовой операции с ясными
   аргументами и надёжной проверкой.
2. **Карта возможностей и поиск** — чтобы обнаружить менее частую операцию,
   проверить, поддерживается ли она, и получить её точную сигнатуру.
3. **Общий типизированный вызов API или Action** — для любой доступной
   низкоуровневой возможности, у которой пока нет отдельной доменной оболочки.

Не проси сервер прислать весь каталог ReaScript или все параметры всех FX. При
этом не делай вывод, что возможности нет, лишь потому что не увидел отдельную
доменную команду: проверь карту и поиск.

Перед низкоуровневым вызовом проверь по карте возможностей как минимум:

- точное имя и сигнатуру;
- версию REAPER и доступность функции в текущем экземпляре;
- можно ли вызвать её через установленный bridge;
- какие объекты и типы аргументов нужны;
- читает ли она состояние, изменяет проект, запускает внешний эффект или
  может ли быть надёжно отменена.

Статусы «описано в документации», «реализовано в библиотеке», «доступно в этой
версии REAPER» и «вызов поддержан текущим bridge» — разные факты. Не смешивай
их и не представляй неподтверждённый вызов как готовую возможность.

## Поиск API: отправляй структурированное намерение

Не передавай в поиск исходный запрос пользователя свободным текстом. В нём
могут быть несколько операций и разные типы объектов. Сначала разложи
намерение на отдельные вопросы о возможностях и передай для каждого короткую
карточку:

- `object` — объект REAPER: дорожка, media item, take, MIDI item, FX, envelope,
  маркер темпа и т. п.;
- `operation` — одно действие: прочитать, найти, разрезать, переместить,
  изменить, вставить, удалить и т. п.;
- `qualifiers` — существенные условия: по времени проекта, по GUID, относительно
  сетки, на конкретную дорожку и т. п.;
- `detail` — имена, краткие сигнатуры либо полная документация;
- `limit` — небольшое число кандидатов, достаточное для выбора.

Пример поиска функции разрезания media item по времени проекта:

```json
{
  "object": "media_item",
  "operation": "split",
  "qualifiers": ["at_project_time"],
  "detail": "summary",
  "limit": 5
}
```

Если запрос включает перемещение дорожки и разрезание item, ищи эти операции
отдельно. Используй точное имя API, если оно уже известно. Если первый набор
результатов неубедителен, уточни карточку, запроси подробности или просмотри
карту нужного домена. Не исполняй первый найденный кандидат автоматически.

Пользовательская формулировка задаёт **цель**, но не обязана совпадать с
терминами API. Поиск нужен для нахождения строительных блоков; музыкальное
решение принимает модель с учётом проекта и пожелания пользователя.

## Установи контекст проекта

Перед действиями, зависящими от проекта:

1. Проверь состояние подключения, версию REAPER и список открытых проектов.
2. Выбери однозначный `project_id`. Не предполагай, что активный проект — тот,
   который пользователь имел в виду, если открыто несколько проектов.
3. Прочитай компактный снимок проекта. Для задачи запроси дополнительные поля,
   которые влияют на решение: выбранные объекты, items и takes, FX, sends,
   folders/buses, автоматизацию, MIDI, сетку, размер такта, транспорт или
   положение курсора.
4. Для адресации изменений используй стабильные GUID и ревизию проекта.
   Название или индекс дорожки сами по себе не являются надёжным адресом.

Считай неизвестное неизвестным. Если FX-параметр, состояние маршрута, источник
аудио или возможность функции не были прочитаны, не утверждай, что знаешь их.
Уточни только недостающий факт, который действительно влияет на безопасный
выбор операции.

### Темп и музыкальная сетка

Для задач, связанных с ритмом, используй карту темпа и размера такта по времени
проекта. Одного базового BPM недостаточно, если в проекте есть маркеры или
автоматизация темпа. Выясняй BPM и метр в целевой временной точке или интервале;
не применяй одно значение ко всему проекту при меняющемся темпе.

Не угадывай, означает ли пользовательская цель четверти, восьмые, шестнадцатые,
триоли или другую сетку. Выведи подходящее подразделение из материала,
контекста и запроса, а если выбор существенно меняет результат и неочевиден —
задай один короткий уточняющий вопрос или сначала подготовь preview.

## Анализ и прослушивание аудио

Когда пользователю нужен анализ звучания, предпочитай один пакетный запрос,
который запускает все подходящие включённые анализаторы для целевого участка и
возвращает согласованный результат. Не вызывай измеритель отдельно для каждой
дорожки и не заставляй модель вручную агрегировать показатели, которые сервер
может выдать одним вызовом.

Если задача требует сравнения с референсом или двух участков, передай их вместе
с тем же запросом, когда контракт инструмента это поддерживает. Иначе используй
отдельный инструмент сравнения, найденный в фактической карте возможностей.
Не запускай попарное сравнение всех дорожек без нужды: число пар быстро растёт.

Результат анализа должен связывать аудио с состоянием проекта. Для каждой
дорожки и мастера используй доступные данные о GUID, pan, fader, mute/solo,
FX, маршрутах, временном диапазоне и точке съёма. В каждом временном сегменте
показывай темп, применимый в этой части проекта, а не только базовый BPM.

Различай источники сигнала:

- дорожечный capture;
- выход bus/folder, если он снимается отдельно;
- полный master mix с обработкой master FX.

Официальная документация REAPER указывает, что `GetAudioAccessorSamples`
возвращает track-сэмплы непосредственно **до FX дорожки**. Такой AudioAccessor
можно использовать как raw pre-FX источник, но нельзя выдавать за обработанный
микшерный stem: в нём нет track FX, и он не равен выходу дорожки в миксе. Не
предполагай, что обычный stem содержит обработку master-шины или равен мастеру.
Используй метаданные точки съёма и фактический результат. Не считай
одновременно folder-output и входящие в него дорожки отдельными независимыми
источниками для суммирования, если анализатор не помечает эту связь.

Открой и прослушай аудио-ресурс, если текущий MCP-клиент действительно
передаёт звук модели. Сам факт существования URI или числовых метрик не означает,
что модель услышала запись. Если клиент не передал аудио для прослушивания,
укажи, что оценка основана на измерениях, а не на слуховом подтверждении.

Если задача связана с таймингом, транзиентами или нарезкой, передай
`analysis_id` в `reaper_edit_map`. Он вернёт кандидаты резов и свидетельства о
стыках, но не изменит проект. По умолчанию карта не решает, что резать или
оставлять, и не угадывает группы источников; `decide=true` явно запрашивает
эвристические метки, а `source_groups` передаёт вызывающая сторона. Сверь
кандидаты с объектами проекта, прежде чем готовить правки через `reaper_edit`.

Временные WAV и отчёты анализа — ограниченные артефакты с TTL. Не копи стемы,
не сохраняй их в плейлисте и не создавай долговечные версии на каждый анализ.
После срока хранения используй только отчёт или аудио, которые ещё доступны.

## Как выполнять произвольную музыкальную задачу

У задачи нет обязательного рецепта. Выбирай кратчайшую последовательность,
которая сохраняет необходимый контекст и даёт проверяемый результат:

1. Сформулируй целевое изменение или ответ и выяви объекты, которых оно касается.
2. Получи только нужный контекст проекта; пакетируй независимые чтения и анализ.
3. Если непонятно, какими средствами REAPER может выполнить часть цели,
   найди соответствующие общие операции в карте и API-поиске.
4. Если цель меняет проект, сгруппируй связанные операции и сначала покажи
   preview, когда он доступен. Не делай бессмысленный preview для чистого чтения.
5. Примени одобренный/явно запрошенный план к ожидаемой ревизии.
6. Прочитай обратно изменённые объекты и проверь результат подходящим способом:
   состояние проекта, метрики, сравнение участков или прослушивание.
7. Исправляй только выявленную проблему. Не повторяй всю операцию вслепую.
8. Сохраняй проект только в соответствии с просьбой пользователя и политикой
   конфликта файлов.

Это ориентиры, а не жёсткий workflow: простая просьба может требовать меньше
шагов, сложная — поиска дополнительных возможностей. Объединяй совместимые
операции и анализ в один вызов, если это уменьшает число round trips и не
скрывает промежуточный результат, важный для безопасного решения.

### Открытые музыкальные цели

Открытая музыкальная цель не задаёт отдельную функцию или заранее заданный
порядок действий. Модель выясняет, какие общие возможности подходят текущему
проекту и запросу, затем проверяет получившийся результат. То же правило
относится к MIDI, FX, маршрутизации, автоматизации, сведению и другим задачам:
интерфейс не должен подменять пользовательское намерение прошитым музыкальным
рецептом.

## Изменения без потери контекста

Для изменения проекта:

- Указывай `project_id`, ожидаемую ревизию и GUID объектов.
- Объединяй связанные операции в один план, если библиотека способна безопасно
  применить и проверить их вместе.
- Используй preview, чтобы показать конкретные объекты и ожидаемый diff.
- При apply проверяй актуальность ревизии и повторно проверяй адресуемые GUID.
- После применения считывай фактическое состояние и получай новую ревизию.
- Если результат не совпал с планом, остановись, исследуй причину и откати
  собственную undo-группу, если такая отмена заявлена и доступна.
- Не объявляй произвольный API-вызов или Action отменяемым только по его имени.
  Если библиотека не может гарантировать undo, обозначь его эффект до вызова.

После ошибки устаревшей ревизии не повторяй запись с прежними аргументами.
Сними актуальный контекст, выясни, что изменилось, и построй план заново.
После сетевой ошибки с неопределённым исходом сначала проверь фактическое
состояние, чтобы не выполнить одну правку дважды.

`reaper_edit` поддерживает пакетные kinds, которые сейчас объявлены в
`reaper_capabilities`: `track.set`, `track.create`, `track.delete`,
`track.reorder`, `item.set`, `item.create`, `item.delete`, `item.split`,
`item.duplicate`, `take.set`, `midi.create`, `fx.set_enabled`,
`fx.set_parameter`, `fx.insert`, `fx.delete`, `fx.set_preset`, `fx.move`,
`fx.offline`, `send.set`, `send.create`, `send.delete`, `marker.create`,
`region.delete`, `envelope.set`, `tempo.set`. У каждого kind свой строгий
контракт `values`; preview/bridge возвращает явную ошибку, если объект или
значение не поддерживается. Для любого другого документированного действия
сначала ищи API/Action, а затем оцени, можно ли безопасно проверить и отменить
его результат.

Для item.split параметр tail_s задаёт полное удлинение левого айтема после
исходной точки реза. Параметры move_s и right_trim_s сдвигают начало правого
айтема; right_trim_s — временной сдвиг в проекте, а не обрезка исходного аудио
тейка. Геометрия кандидата: left_end = cut + tail_s,
right_start = cut + move_s + right_trim_s, overlap = left_end - right_start.
Если перекрытие положительное, оба фейда равны его фактической длине; при
зазоре применяется заданный fade_s на краях айтемов. Поиск шва измеряет обе
границы перекрытия в собранном аудио и ранжирует по худшей. При применении
строки поиска передавай left_extend_s как tail_s с тем же числом; не добавляй
move_s или right_trim_s повторно. После apply считывай позиции айтемов и фейды
из REAPER.

Обычный вызов `reaper_api_call` требует точное имя из каталога, позиционный
массив `values`, `project_id` и полную `expected_revision`. Аргументы
host-object передавай как стабильную ссылку, например
`{"$reaper_ref":{"kind":"MediaTrack","guid":"{TRACK-GUID}"}}`; для
параметра `ReaProject` используй `{"$reaper_ref":{"kind":"ReaProject"}}`.
Полученный `{"$reaper_handle": ...}` передавай обратно целиком. `null` разрешён
только для optional-параметров сигнатуры; аргумент типа `reaper.array` задаётся
числовым JSON-массивом. Opaque handle истекает при смене ревизии или перезапуске
bridge. После низкоуровневого вызова перечитай проект: произвольный API не
получает автоматическую транзакционную отмену.

Для Actions используй `reaper_action(mode="search", query_object=...,
query_operation=...)`. Вызов требует `command_id`, `project_id` и
`expected_revision`: `section_id=0` — главная секция, `section_id=32060` —
MIDI Editor с активным окном редактора. Action не считается отменяемым только
потому, что у него есть Undo в пользовательском меню.

## Сохранение и артефакты

Не сохраняй проект и не перезаписывай файл молча. При просьбе сохранить
используй REAPER API и понятное имя. Если такой файл уже существует, прочитай
результат конфликта и выбери новый путь или запроси необходимое решение; не
считай наличие разрешения перезаписать файл само собой разумеющимся.

Поддерживай исходный вариант и актуальный финальный вариант. Не создавай
неограниченную цепочку копий проекта и не сохраняй промежуточный стем после
каждой итерации. Временные артефакты анализа удаляются по TTL. Для сравнения
до/после используй сохранённый исходник и финальный результат, если пользователь
попросил оставить оба.

`reaper_analyze` по умолчанию передаёт аудиофайлы во временное внешнее
workspace с manifest. Оно не добавляет WAV в `.RPP` и не создаёт дорожки.
Ресурсы отчёта и WAV доступны по URI вида
`reaper://analyses/{analysis_id}/report` и
`reaper://analyses/{analysis_id}/audio/{source_guid}`. Срок аренды — один час;
хранится не больше одного результата каждой роли `temporary`, `baseline`,
`final`. Замена роли удаляет её предыдущие зарегистрированные файлы, а
`reaper_release` очищает выбранный результат немедленно. Просроченные файлы
удаляются только по валидному manifest.

## Долгие операции и ошибки

Анализ в текущей MCP-версии синхронный; отдельного `job/status/cancel` tool
пока нет. Для короткого запроса указывай только нужный диапазон, если это
подходит задаче. Пока вызов выполняется, не запускай дублирующий анализ. После
таймаута сначала проверь состояние bridge и текущий проект: операция могла
закончиться, даже если клиент не получил ответ.

При ошибке используй код, сообщение и `next_action` из ответа:

- **stale revision** — обнови контекст и перепланируй;
- **unsupported/unavailable** — сообщи, какая часть недоступна, затем проверь
  альтернативные возможности через карту/API-поиск;
- **validation error** — исправь тип, обязательное поле или диапазон по схеме;
- **ambiguous target** — уточни объект, не выбирай по совпадению имени наугад;
- **bridge timeout** — сначала проверь фактическое состояние REAPER, не дублируй вызов.

Не выдумывай успешный исход, сигнатуру, измерение или прослушивание. Отделяй
факт от вывода и явно называй ограничения результата.

## Что сообщить пользователю по завершении

Кратко сообщи:

- что проверено или какие объекты изменены (для неоднозначных объектов — имя и
  понятный признак, а внутри API — GUID);
- подтверждён ли результат чтением обратно, анализом и/или прослушиванием;
- новую ревизию проекта, если это помогает следующей операции;
- что не удалось подтвердить и почему;
- был ли проект сохранён и какие временные артефакты будут удалены.

Не называй числовой анализ слуховой оценкой. Не пиши «готово», если операция
вернула ошибку, проверка не состоялась или часть целевой задачи осталась
невыполненной.

## Проверка качества интерфейса

Перед выпуском сервера проверь этот README и инструменты на разнообразных
задачах, включая неиспользованные при проектировании: управление FX,
маршрутизацию, автоматизацию, MIDI, tempo map, редактирование media items,
сохранение, захват звука и сравнение. Измеряй полноту обнаружения нужных
возможностей, пропуски существующего инструмента, неверные вызовы, число
round trips, размер контекста, точность чтения результата, возможность отката
и число неожиданных изменений состояния.

Задача считается поддержанной, только если модель может обнаружить подходящую
возможность, получить корректные аргументы, выполнить её через документированный
путь и проверить исход. Если операция пока не поддержана, карта должна показать
это честно, а README — научить модель находить доступные альтернативы, не
создавая ложного обещания полного покрытия.
