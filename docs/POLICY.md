# Политика проекта: пороги, которые задаёт человек

Все числа здесь — **настройки проекта и доставки**, а не константы метода.
Библиотека не содержит их в коде; она читает политику и возвращает нарушения.
Если политика не задана, гейты только измеряют и ничего не запрещают.

## Ключи

| Ключ | Что ограничивает | Откуда берётся значение |
|---|---|---|
| `max_clip_runs` | прогоны на полной шкале + плоские вершины | политика проекта; 0 — «ни одного сэмпла» |
| `max_dc` | постоянная составляющая | политика проекта |
| `max_silence_s` | longest run тишины внутри материала | политика проекта |
| `max_level_jump_db` | шаг RMS между окнами 1 с | **только внутри секции**: на границе «тихое интро → группа» это музыкальная динамика, а не дефект |
| `max_true_peak_dbtp` | true peak (BS.1770 Annex 2) | спецификация доставки: −1 dBTP для стриминга, −2 dBTP для Amazon/броадкаста |
| `alignment.max_slope_sigma` | во сколько сигм наклон дрейфа считается значимым | политика проекта; без него `action` не вычисляется |
| `alignment.min_correlation` | ниже какой медианной корреляции выравнивание не доверять | политика проекта |

## Пример (не эталон)

```json
{
  "max_clip_runs": 0,
  "max_dc": 0.001,
  "max_silence_s": 0.5,
  "max_level_jump_db": 12,
  "max_true_peak_dbtp": -1.0
}
```

## Жёсткие правила процесса, которые политикой не выражаются

Из ремесленной практики (источники — `docs/mix-craft.md`), это шаги, а не пороги:

1. **Перед сравнением с референсом уравнять громкость** (в пределах ~0.5 дБ);
   иначе «громче» читается как «лучше».
2. **Референс идёт мимо мастер-цепочки**, сравнение короткими фрагментами
   одного типа (припев с припевом), на 2–3 системах.
3. **Дизер — только при финальном понижении разрядности**, не в промежуточных
   рендерах.
4. **Полное прослушивание мастера** перед сдачей — человеком; библиотека этот
   шаг не заменяет, а готовит к нему отчёт.

Пункты 1–3 библиотека может проверить по журналу (какая громкость была у
сравниваемых файлов, был ли дизер, какой рендер финальный), пункт 4 — нет.
